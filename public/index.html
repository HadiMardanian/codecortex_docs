CodeCortex چیست؟
موتور کانتکست برای ایجنت‌های برنامه‌نویسی

«قبل از اینکه ایجنت حدس بزند، ریپو باید بتواند خودش را توضیح بدهد.»

CodeCortex یک ابزار متن‌باز (Apache 2.0) است که بین ایجنت هوش‌مصنوعیِ شما (مثل Claude Code، Cursor یا Codex) و کدبیستان می‌نشیند. کل ریپو را ایندکس می‌کند — ساختار، توابع، روابط، تاریخچهٔ Git، تصمیم‌های تیم — و برای هر سؤال یا تسک، کوچک‌ترین بستهٔ شواهدِ مفید را تحویل ایجنت می‌دهد؛ به‌جای اینکه مدل مجبور شود نصف ریپو را باز کند و همه‌چیز را از صفر حدس بزند.

🚀 شروع در ۶۰ ثانیه 💼 Use caseهای کاربردی 🔍 از اول بخوان
🐍 Python 3.11–3.13 📄 Apache 2.0 🧪 711 تست پاس‌شده ⚡ جست‌وجوی تعریف: ~0.2ms 🧭 وضعیت: Alpha
■ بخش ۱ — توضیح ساده

CodeCortex در یک جمله + یک تشبیه

💡 تعریف رسمی (ترجمهٔ ساده)
«CodeCortex یک ریپوی نرم‌افزاری را به یک سیستم شواهدِ مخصوص همان سؤال تبدیل می‌کند تا ایجنت برنامه‌نویسی، به‌جای حدس زدن، با نقشه و مدرک جلو برود.»

تشبیه: فرض کنید یک مهندس نابغه استخدام کرده‌اید (مدل هوش مصنوعی) ولی به او نه نقشهٔ ساختمان داده‌اید، نه چارت سازمانی، نه مستندات و نه تاریخچهٔ پروژه. هر روز ساعت‌ها وقتش صرف گم‌شدن می‌شود. CodeCortex همان کتابخانه‌دار و راهنمای ساختمان است که کنارش می‌ایستد و می‌گوید: «برای این سؤال، این ۵ فایل، این ۱۲ فراخوانی، این ۲ تغییر اخیر و این تصمیم قدیمی تیم را ببین — همین و بس.»

  • ❌ یک چت‌بات دیگر نیست.
  • ❌ سرویس‌دهندهٔ مدل (Model Provider) نیست و خودش هوش مصنوعی اجرا نمی‌کند.
  • ❌ ادعا نمی‌کند ایجنت را بی‌خطا می‌کند.
  • ✅ زیرساخت کانتکست است: چیزی که کیفیت اطلاعاتِ ورودی به استدلال (reasoning) ایجنت را بهتر می‌کند.
⭐ قاعدهٔ طلایی پروژه
«اول evidence را پیدا کن، بعد با confidence حرف بزن.» — یعنی: اول مدرک، بعد اطمینان.
■ بخش ۲ — مسئله

چه مشکلی را حل می‌کند؟

مدل قوی می‌تواند کد بخواند؛ مسئلهٔ سخت این است که بداند کدام کد اهمیت دارد، چه چیزی به چه چیزی وصل است، چه چیزی عوض شده، و اگر تغییر اشتباه باشد چه چیزی می‌شکند.

😩 بدون موتور کانتکست (جریان حدس‌زدن)

جست‌وجوی اسم فایل → باز کردن فایل‌های بزرگ → کشفِ دوبارهٔ معماری → حدس رفرنس‌ها → گشتنِ دستی در Git → حدس وسعت آسیب → مصرف زیاد کانتکست → ویرایش → کشفِ دیرهنگام یک وابستگی پنهان!

😎 با CodeCortex (جریان شواهدمحور)

تسک → تشخیص نیت → جمع‌آوری شواهد → رتبه‌بندی برای همین تسک → حفظ منبع و عدم‌قطعیت → جا شدن در بودجهٔ توکن → یک سطح واحد برای ایجنت → اعتبارسنجی تغییرِ پیشنهادی
🎯 نکتهٔ کلیدی
هدف «کانتکست بیشتر» نیست؛ هدف «شواهدِ مفیدتر به‌ازای هر توکن» است. پنجرهٔ کانتکست بزرگ این مشکل را حل نمی‌کند — کیفیت شواهد و حجم آن دو مسئلهٔ جدایند.

۹ جزء داخلی (از سند ARCHITECTURE رسمی — ساده‌شده)

🚪

Gateway (درب ورودی)

هر درخواست از CLI یا MCP اول از اینجا وارد می‌شود.

🧭

Router (مسیریاب)

نیتِ سؤال را تشخیص می‌دهد: «تعریف می‌خواهی؟ impact؟ تاریخچه؟» و موتورهای درست را انتخاب می‌کند.

🎼

Orchestrator

نقشهٔ مسیر را اجرا می‌کند و نتایج موتورها را ترکیب می‌کند.

⚙️

Engines (موتورها)

ریپو، سیمبل، کانتکست، حافظه و اعتبارسنجی — هرکدام یک توانایی جدا و قابل‌جایگزین.

📦

Context Pipeline

شواهد را رتبه‌بندی، حذف‌تکرار و برش می‌زند تا داخل «بودجهٔ توکن» جا شوند.

🧠

Memory (حافظه)

تصمیم‌ها و حقایق ماندگار پروژه و تیم را نگه می‌دارد — فراتر از یک چت.

🔬

Evidence Providers

سه لایهٔ کاملاً اختیاری (دقیق، وابستگی، ساختاری) که شواهدِ قوی‌تر اضافه می‌کنند.

📈

Telemetry

مسیریابی، زمان‌ها و سلامت موتورها را ثبت می‌کند تا رفتار سیستم قابل بازرسی باشد.

🔌

Interfaces

سطح‌های اتصال: CLI، سرور MCP و APIهای آینده.

⚠️ مهم‌ترین اصل معماری
سورس کد همچنان منبع حقیقت است. گراف، حافظه، جست‌وجوی معنایی و خلاصه‌ها فقط «برای فهم بهتر» هستند و هیچ‌وقت جای سورس فعلی، کانفیگ و تست‌ها را نمی‌گیرند.
■ بخش ۴ — قابلیت‌ها

چه کارهایی از دستش برمی‌آید؟

قابلیتبه زبان ساده یعنی...
🗺️ نقشهٔ ریپوهمهٔ فایل‌ها و ساختار پروژه را ایندکس می‌کند تا ایجنت یک نقشهٔ محدود و دقیق داشته باشد، نه یک جنگل پوشه.
🔤 سیمبل‌های چندزبانهتوابع، کلاس‌ها و متغیرها را با «هویت» می‌شناسد — نه فقط با جست‌وجوی اسم فایل. تعریف و رفرنس هر نماد را دقیق پیدا می‌کند.
🕸️ گراف وابستگی و فراخوانیثبت می‌کند چه کسی چه کسی را صدا می‌زند و چه کسی به چه کسی وابسته است — پایهٔ navigation و تحلیل impact.
🔍 جست‌وجوی هیبریدیسه نوع جست‌وجو با هم: واژگانی (کلمه‌ها)، معنایی (مفهوم) و ساختاری (شکل کد در AST) — چون «کد، متنِ معمولی نیست».
🕰️ هوش Git و PRتاریخچه، blame، مالکیت و churn هر فایل/سیمبل قابل پرس‌وجو می‌شود؛ دیفِ هر PR به سیمبل‌ها، تست‌های متأثر و امتیاز ریسک وصل می‌شود.
💥 تحلیل Impact (شعاع آسیب)قبل از ویرایش می‌گوید: «اگر این را عوض کنی، این ۲۳ فراخوانی و این ۴ تست تحت‌تأثیرند.»
🏛️ معماری و Driftمعماریِ واقعی کد را (با سطح اطمینان) استنباط می‌کند، یک اثرانگشت ذخیره می‌کند و بعداً انحراف معماری را گزارش می‌دهد.
🧠 حافظهٔ پروژه و تیمتصمیم‌های ماندگار مثل «JWT را گذاشتیم چون...» ذخیره می‌شود تا ایجنت دوباره رویکرد ردشده را پیشنهاد ندهد.
✏️ ویرایش کنترل‌شدهrename/replace/insert معنایی با preflight، و مهاجرت‌های ساختاری که اول preview می‌دهند، هش‌چک می‌شوند، اتمیک می‌نویسند و rollback دارند.
🔌 سرور MCPیک سطح استاندارد که ایجنت‌های MCP-پذیر به آن وصل می‌شوند؛ همهٔ قابلیت‌ها از یک دری.
🧪 دقت سیمبل (Precision)وقتی دو پکیج هم‌نام کلاس export می‌کنند، با هویت سیمبل تشخیص می‌دهد کدام‌کدام است — نه شیرِ‌یا‌خطا.
📚 هوش وابستگیتفکیک «نسخهٔ اعلام‌شده» از «نسخهٔ واقعاً resolve‌شده» و پاسخ به اینکه ریپو واقعاً کدام API را اجرا می‌کند.
🖥️ داشبورد Observatoryسلامت موتور، traceها، drift معماری و ریسک PRها را یک‌جا نشان می‌دهد.
🌐 فضای کاری چندریپوییfrontend/backend/contracts جدا هستند ولی جست‌وجو و شواهد بین‌شان federate می‌شود.

۸ دکترین (قوانین مهندسی، نه شعار تبلیغاتی)

⚖️

۰۱ — اول شواهد، بعد اطمینان

دقیق، استنباطی، مبهم، گمشده یا کهنه — هر مدرک با برچسب جداگانه گزارش می‌شود، نه همه با یک سطح اطمینان.

📦

۰۲ — کوچک‌ترین کانتکستِ کافی

بهترین بسته، بزرگ‌ترین چیزی که جا شود نیست؛ کم‌حجم‌ترین چیزی است که برای همین تسک کافی باشد.

📜

۰۳ — سورس، سورس می‌ماند

حافظه «چرا» را توضیح می‌دهد، Git «چطور رسیدیم»، گراف «چه چیزی به چه چیزی» — ولی حقیقتِ اجرایی فقط سورس، کانفیگ و تست است.

❓

۰۴ — ابهام خودش اطلاعات است

اگر دو سیمبل محتمل‌اند، ایجنت باید هر دو را ببیند؛ «در دسترس نیست» بهتر از «موفقِ ساختگی» است.

💥

۰۵ — هر تغییر شعاع آسیب دارد

دیف کوچک می‌تواند پرریسک باشد و دیف بزرگ می‌تواند مکانیکی. سؤال درست: چه کسی به این وابسته است و کدام تستش را پوشش می‌دهد؟

🔒

۰۶ — لوکال‌فرست یک تصمیم اعتماد است

هسته بدون اینترنت کار می‌کند؛ هر مرز شبکه‌ای، کلید و انتقال داده باید صریح و قابل‌مشاهده باشد.

🔁

۰۷ — بازتولیدپذیری از عددِ چشمگیر مهم‌تر است

ادعای عملکرد بدون spec، محیط و artifact قابل بازتولید، شاهد نیست — این پروژه اعداد ساختگی منتشر نمی‌کند.

🧩

۰۸ — مقیاس با هماهنگی صریح

ورکرها هویت، قابلیت و lease دارند؛ حافظهٔ مشترک قواعد تعارض دارد؛ ابزار ریموت auth و policy دارد.

■ بخش ۶ — لایهٔ Evidence Fusion

به هر جواب می‌گوید «چقدر مطمئن است»

جالب‌ترین ایدهٔ CodeCortex این است که هر نتیجه‌ای که به ایجنت می‌دهد، یک درجهٔ اعتماد (trust tier) دارد؛ یعنی ایجنت می‌داند این جواب «دقیق» است یا فقط یک «حدسِ قوی»:

درجهٔ اعتمادیعنی چه؟از کجا می‌آید؟
exact — دقیققطعی و تازهایندکس یا کامپایلرِ تازه
near_exact — تقریباً دقیقحل‌شدهٔ زندهLanguage Server زنده
structural — ساختاریتطابق نحوی واقعیپارس AST یا داکیومنتِ هم‌نسخه
inferred_high — استنباط قویرابطهٔ گرافی قویگراف، یا شاهد exact کهنه‌شده
inferred — استنباطیحدسِ بین‌فایلیهیوریستیک‌های رابطه
weak — ضعیفتصادفِ کلماتتطابق لغوی ساده

سه قانون محافظتی که در کد اجرا می‌شوند (نه فقط در مستندات!)

  1. شاهد کهنه هرگز بالاتر از شاهد ساختاریِ تازه رتبه نمی‌گیرد. دادهٔ exact اما قدیمی، توی امتیازش ضریب می‌خورد و پایین می‌رود.
  2. «exact» و «کهنه» هرگز هم‌زمان نمی‌شوند. دقت دربارهٔ «الان» است؛ چیزی که تاریخ گذشته شده نمی‌تواند دقیق باشد.
  3. هیچ لایه‌ای نمی‌تواند درجهٔ اعتماد خودش را بالا ببرد. سقف اعتماد به «روش» بستگی دارد، نه به اعتمادبه‌نفسِ موتور.
🧩 سه لایهٔ اختیاری که شواهد را تقویت می‌کنند
۱. Precision Code Intelligence: از ایندکس کامپایلری استفاده می‌کند تا تعریف/رفرنس را با هویت سیمبل حل کند.
۲. Dependency Intelligence: manifest + lockfile + نسخهٔ واقعی را کنار هم می‌گذارد و داکیومنتِ همان نسخه را می‌آورد.
۳. Structural Search & Rewrite: کد را با الگوی نحوی پیدا می‌کند — فراخوانیِ واقعی old_api($X) را می‌بیند، نه کامنتی که اسمش را آورده!

هر سه اختیاری‌اند؛ هستهٔ CodeCortex بدون هیچ‌کدام و بدون اینترنت دقیقاً مثل قبل کار می‌کند.
■ بخش ۷ — شروع سریع (واقعاً ۶۰ ثانیه)

نصب و اولین اجرا

پیش‌نیاز: Python 3.11 تا 3.13. همین!

  1. نصب پکیج: 
    python -m pip install --upgrade codecortex-context-engine
    اختیاری: پارسرهای بیشتر pip install "codecortex-context-engine[parsers]" · جست‌وجوی معنایی عصبی لوکال pip install "codecortex-context-engine[semantic]"
  2. داخل ریپو، راه‌اندازی و ایندکس: 
    # داخل پوشهٔ پروژه‌تان
cortex init .      # ساخت کانفیگ در .codecortex/
cortex index       # ساخت ایندکس و گراف ریپو
cortex doctor      # چک سلامت: چه چیزی فعال/غایب است
  3. از ریپو سؤال بپرسید: 
    cortex architecture                        # معماری ریپو را استنباط کن
cortex semantic "authentication and session lifecycle"
cortex impact AuthService                  # اگر این را عوض کنم چه می‌شکند؟
cortex symbol-history src/auth.py 10 80    # تاریخچهٔ یک سیمبل
  4. یا ریپو را به ایجنت برنامه‌نویسی وصل کنید: 
    cortex mcp --path .
  5. دموی آماده را ببینید (اختیاری): 
    # داخل کلون خود ریپوی CodeCortex
python scripts/demo.py    # ایندکس ریپوی نمونه + تحلیل blast radius + routing
✅ نتیجهٔ cortex doctor چه می‌گوید؟
وضعیت هر لایه: available (فعال) · stale (ایندکس قدیمی) · unavailable (نصب نیست) · disabled (خاموش) — و هیچ‌وقت «غایب» را «موفق» جل نمی‌دهد.
■ بخش ۸ — اتصال به ایجنت‌های برنامه‌نویسی

با Claude Code، Cursor، Codex و... حرف بزند

CodeCortex یک سرور MCP (Model Context Protocol) داخلی دارد — یعنی ایجنت‌هایی که MCP را پشتیبانی می‌کنند می‌توانند مستقیم از قابلیت‌هایش استفاده کنند. کانفیگرِ خودش، ورودی مربوط به CodeCortex را به‌صورت merge-safe به فایل کانفیگ ایجنت اضافه می‌کند و بقیهٔ تنظیمات شما دست‌نخورده می‌ماند (با بکاپ هم می‌گیرد):

ایجنتفایل کانفیگ
Claude Code.mcp.json
Codex.codex/config.toml
Cursor.cursor/mcp.json
Gemini CLI.gemini/settings.json
OpenCodeopencode.json
# ۱) ببین چه ایجنت‌هایی نصب است
cortex agents detect

# ۲) اول بدون تغییر — پیش‌نمایش بگیر
cortex agents configure --dry-run

# ۳) همه را یک‌جا وصل کن
cortex agents configure --all

از این بعد ایجنت شما می‌تواند این‌ها را مستقیم درخواست کند: نقشهٔ ریپو، جست‌وجوی سیمبل، رفرنس‌ها، گراف وابستگی، تحلیل impact، جست‌وجوی هیبریدی، «کانتکست فشرده با بودجهٔ مشخص»، معماری، تاریخچهٔ Git، تحلیل PR، حافظهٔ پروژه، جست‌وجوی چندریپویی، traceها و اعتبارسنجی.

تازه وارد تیم شده‌اید. به‌جای باز کردن فایل‌های تصادفی:

cortex architecture        # معماری واقعی با سطح اطمینان
cortex semantic "billing and invoice lifecycle"   # مسیر قلمرو کاری
cortex dashboard           # داشبورد: نقاط داغ گراف، drift، ریسک PRها

چه به‌دست می‌آورید؟ ماژول‌های واقعی، جهت وابستگی‌ها، نقاط داغ (hotspot) — قبل از خواندن حتی یک خط کد.

🐛 ۲ — دیباگ: «لاگین بعضی کاربرها رندوم fail می‌شود»

شروع با: semantic + سیمبل + تاریخچهراستی‌آزمایی: تست‌های هدفمند
cortex semantic "session refresh and token expiry"
cortex impact refresh_token            # چه کسی به این وابسته است؟
cortex symbol-history src/auth.py 10 80  # اخیراً چه عوض شده؟ چه کسی مالکش است؟

بررسی درست باید جواب بدهد: رفتار کجا پیاده شده؟ چه callerهایی در مسیرند؟ چه چیزی اخیراً عوض شده؟ کدام مسیر جایگزین فرضیه را رد می‌کند؟ کدام تست باید fail شود اگر توضیحت غلط است؟ کوچک‌ترین تغییر امن چیست؟ — CodeCortex این شش سؤال را یک‌جا جواب می‌دهد.

🔧 ۳ — ریفکتور امن: rename در کل ریپو

شروع با: references + impactراستی‌آزمایی: ویرایش مرحله‌ای + تست‌های قراردادی
cortex references src/auth.py 12 7    # همهٔ رفرنس‌های این سیمبل
cortex impact AuthService             # ۲۳ caller و ۴ تست متأثر
cortex edit rename src/auth.py AuthService SessionService
# بعدش: اعتبارسنجی و تست‌ها

نظم تغییر در CodeCortex: «به‌اندازهٔ کافی بخوان ← impact را بفهم ← محدود تغییر بده ← اعتبارسنجی کن». نه: «همه‌جا replace کن ← امیدوار باش تست‌ها بگیرند!»

📦 ۴ — مهاجرت وابستگی: کامل‌ترین سناریو (مثال رسمی مستندات)

شروع با: imports + usage + فرض‌های نسخهراستی‌آزمایی: چک‌های سازگاری

هدف: «middleware احراز هویت را به APIِ نسخه‌ای که این ریپو واقعاً استفاده می‌کند، مهاجرت بده.» جریان رسمی:

# ۱) نسخهٔ واقعاً resolve‌شده چه است؟ (نه چیزی که manifest ادعا می‌کند)
cortex dependency next

# ۲) همهٔ فراخوانی‌های ساختاری API قدیمی را پیدا کن (نه کامنت‌ها را!)
cortex structural-search --lang python --pattern 'old_api($X)'

# ۳) پیش‌نمایش مهاجرت + تحلیل impact خودکار
cortex rewrite-preview --lang python --pattern 'old_api($X)' --replacement 'new_api($X)'

# ۴) بعد از بازبینی preview — اعمال امن
cortex rewrite-apply <preview-id>

چرخهٔ عمر rewrite (۱۲ گام محافظتی): جست‌وجوی ساختاری ← محدودیت‌ها (تعداد فایل/مطابقت/بایت) ← تحلیل impact ← preview ذخیره‌شده با SHA-256 هر فایل ← اعمال فقط با id و مجوز ← هش‌چکِ دوباره (اگر فایل وسط کار عوض شده باشد، تراکنش abort می‌شود!) ← نوشتن اتمیک با rollback ← reindex ← اعتبارسنجی ← گزارش impact بعد از تغییر.

📊 اثر واقعی (بنچمارک رسمی روی ریپوهای fixture)
تشخیص سیمبل هم‌نام: دقت 0.50 ← 1.00 · تشخیص نسخهٔ resolve‌شده: 0.00 ← 1.00 · مهاجرت مکانیکی: 0.50 ← 1.00

👀 ۵ — بررسی Pull Request: فراتر از «اندازهٔ دیف»

شروع با: سیمبل‌های تغییریافته + impactراستی‌آزمایی: تست‌های متأثر + drift
cortex pr main --head HEAD

خروجی: دیف ← فایل‌های عوض‌شده ← سیمبل‌های عوض‌شده ← impact پایین‌دستی ← تست‌های متأثر ← churn/مالکیت ناحیه ← حرکت معماری ← شواهد ریسک. نتیجه: یک دیفِ ۲۰ خطی که قلبِ auth را لمس می‌کند، درست ریسکی دیده می‌شود؛ نه «یه PR کوچک».

🧩 ۶ — پروژهٔ چندریپویی (frontend + backend + contracts)

شروع با: workspaceهر ریپو هویتش حفظ می‌شود
cortex workspace-add backend ../backend
cortex workspace-add contracts ../contracts
cortex workspace-search "payment service"   # جست‌وجوی فدره‌شده در همهٔ ریپوها

CodeCortex ریپوها را «یکی» جل نمی‌دهد؛ شواهد را فدره می‌کند و رابطه‌های بین‌ریپویی را نگه می‌دارد.

🧠 ۷ — حافظهٔ تیمی: یک بار تصمیم بگیر، همیشه remembered

شروع با: team-rememberتاریخچهٔ revision + تشخیص تعارض
cortex team-remember "برای دسترسی به DB فقط الگوی repository؛ ORM خام ممنوع — تصمیم تیم بک‌اند، ۱۴۰۳"
cortex team-search "database access policy"

حافظهٔ تیمی روی SQLite با WAL است، تاریخچهٔ revision دارد، نوشتهٔ قدیمیِ متعارض را رد می‌کند (نه اینکه بی‌صدا روی جدید رونویسی کند) و metadataِ «چه‌کسی/ازکجا» نگه می‌دارد. ایجنت دیگر هرگز رویکردِ ردشده را از نو پیشنهاد نمی‌دهد.

■ بخش ۱۱ — تیم و سازمان

🌐 مقیاس: از لپ‌تاپ تا استقرار سازمانی

پروفایلشکل معمول
فردی (Solo)ریپوی لوکال ← ایندکس لوکال ← حافظهٔ لوکال ← ایجنت با MCP
تیمقواعد مشترک ← حافظهٔ تیمی ← workspace ← هوش PR
فضای کاری بزرگریپوهای زیاد ← شواهد فدره‌شده ← سطح ریموتِ احراز‌هویت‌شده
توزیع‌شدهgateway ← policy ← coordinator ← ورکرها ← مخازن پایدار

عملیات توزیع‌شده (اختیاری — از سند DISTRIBUTED)

  • سرور ریموت cortex-remote: همان سطح MCP روی HTTP/HTTPS با توکن bearer (مقایسهٔ زمان‌ثابت)، TLS 1.2+، سهمیهٔ per-principal و allow-list ابزارها.
  • حافظهٔ مشترک توزیع‌شده: رپلیکاها با version vector همگام می‌شوند؛ تعارض‌ها determinstic حل می‌شوند؛ حذف‌ها با tombstone رونوشت می‌شوند.
  • ورکرهای چندنودی: صف کار durable؛ هر ورکر قابلیت‌اش (index، retrieve، vector) را اعلام می‌کند و lease دارد؛ کارِ منقضی خودکار دوباره صف می‌شود.
  • Vector Store پایدار: پیش‌فرض SQLite بدون سرویس؛ برای مقیاس بزرگ pgvector/Qdrant/Milvus/Weaviate با ثبت provider قابل اتصال است.
  • سازمان و Audit: نقش‌های owner/admin/member/viewer، policy هر workspace، سقف کانتکست و لاگ audit با retention قابل‌تنظیم.
  • SDK رسمی: کلاینت‌های تایپ‌دار Python و TypeScript برای Platform API.

■ بخش ۱۳ — سوالات متداول

❓ FAQ

❔ جای مدل برنامه‌نویسی را می‌گیرد؟

نه. مدل همچنان استدلال و تولید کد می‌کند؛ CodeCortex فقط «محیط شواهد» را بهتر می‌کند.

❔ به سرویس ریموت نیاز دارد؟

نه. هسته کاملاً لوکال‌فرست و بدون اینترنت کار می‌کند؛ لایه‌های ریموت همه اختیاری‌اند.

❔ پنجرهٔ کانتکست بزرگ، این را بی‌نیاز نمی‌کند؟

نه. اندازهٔ پنجره و کیفیت شواهد دو مسئلهٔ جدایند.

❔ همهٔ روابط دقیق‌اند؟

نه — و این عمدی است. روابط استنباطی ابهام را حفظ می‌کنند؛ لایهٔ Precision وقتی ایندکس کامپایلری موجود باشد شواهد exact اضافه می‌کند.

❔ بین چند ریپو کار می‌کند؟

بله؛ workspaceها شواهد را فدره می‌کنند ولی هویت هر ریپو حفظ می‌شود.

❔ خودش کد را ویرایش می‌کند؟

ویرایش معنایی کنترل‌شده دارد؛ ولی «خواندنِ هوشمند» و «تغییر» دو دسترسی جدایند و تغییر همیشه مجوز و پیش‌نمایش می‌خواهد.
